- **RESOLVED in Phase 4c** — **fire-and-forget init vs Edge runtime**: Phase 4b's `middleware.ts` fired `/api/demo/init` un-awaited (`void fetch(...)`), which the platform could tear down on a serverless **Edge** deployment before seeding finished. Phase 4c confirmed empirically (via a temporary probe + Next's static analysis error "A Node.js API … not supported in the Edge Runtime") that this project's legacy `middleware.ts` compiles for the **Edge runtime** in Next 16.2.12 despite `proxy` defaulting to Node since v16.0 — and moved the seed fetch into `event.waitUntil(...)` (`NextFetchEvent`), the Edge-native primitive whose documented contract extends the serverless invocation lifetime until the promise settles. First-load stays ~250 ms (unblocked) and seeding reliably completes post-response. `after()` was not used: Next documents it for Server Components/Server Functions/Route Handlers/**Proxy**, not the legacy middleware/Edge convention. Client-side bounded retries from Phase 4b remain as a net. The deprecated `middleware.ts` → `proxy.ts` migration (which would also make `after()` available) is a candidate follow-up / Phase 6 task, still out of scope.
- **Phase 4b — CLI seed env gotcha**: `next dev` loads `.env.local` automatically, but `npx prisma db seed` / `npx tsx` do not; `DATABASE_URL` must be set in the process environment. - **Verification environment gotcha**: PowerShell 5.1 `Invoke-WebRequest -Headers @{ Cookie = ... }` silently drops the `Cookie` header (can't be set via `Headers`); any cookie-based verification script should use `curl.exe -H "Cookie: ..."` instead. Stumbled on this during Phase 4b while timing middleware behavior.
- **Verification environment gotcha (Phase 5)**: PowerShell 5.1 mangles inline native-arg JSON passed to `curl.exe -d '{"status":"CLEANING"}'` — the server receives corrupted bytes (JSON parse errors at position 1).
